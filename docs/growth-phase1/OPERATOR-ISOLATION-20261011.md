# STEP 2 — 運営者QAと本番GA4の分離（2026-10-11）

## 目的と既知の事実

- 2026-10-10まで、`?test=1` で識別された運営者操作も本番GA4へ送信され、通常集計に混在する余地があった。
- Windsor.ai GA4（property 558239521）で2026-10-10の日付を再取得できたが、`customevent_operator_test` のget_dataは `Unexpected field(s)` を返す。運営者除外後の人数・順序付き診断完了率は取得できていない。
- 以前のPVやイベントを後から「一般利用者分だけ」と再分類しない。
- 今回の変更でGA4管理画面のセグメントやプロパティ設定は変更しない。購入/売上は楽天側データでしか確定できない。

## 実装

共有 `assets/analytics-context.js` が、GAタグが実行されるより前に `window['ga-disable-G-6STQ5HXRDH']` をセットする。

| ユーザーの状態 | flag / GA4送信 | 意味 |
| --- | --- | --- |
| 通常利用（`?test=1`履歴なし、解析許可） | false / 通常どおり | 既存のPV・診断・クリックイベントを維持 |
| `?test=1` または持続QAモード | true / 抑止 | 本番計測へ運営者テストを送信しない |
| QA中に解析トグルをON | true / 引き続き抑止 | テスト隔離を勝手に解除しない |
| `?test=0` でQAを解除＋解析許可 | false / 通常どおり | 実利用に戻す |
| 既存の解析停止設定（2キーのどちらか） | true / 抑止 | プライバシー選択を維持 |

Google公式: https://developers.google.com/tag-platform/security/guides/privacy#turn_off_google_analytics

`gtag` の呼び出しと `dataLayer` のイベントは残るので、送信遮断したブラウザ回帰テストで計測イベントの内容を検証できる。ただしQAモードのイベントがGA4 Realtimeへ到着することは期待しない。必要なら本番とは別の検証ストリームでテストすること（本PRでは新設しない）。

共通スクリプトのキャッシュキーは主要4ページで更新。`scripts/stamp_assets.py` は公開ビルド時に全HTML内のキーを現行ハッシュへ更新する既存処理である。新しいGA4のID・端末識別子・Cookie・外部送信先は追加しない。

## 受け入れ条件

1. `?test=1` のHOME→CAMP→CAR STAY→FISHINGでフラグがtrue、`dataLayer` の既存イベント形式は維持。
2. テスト中に解析ONを選んでもGA4送信の抑止を維持。
3. `?test=0` かつ解析ONならフラグfalse、通常の測定を維持。
4. 既存解析停止の2キーは従来どおり有効。
5. `npm run check`、`npm test`、成長監査、ブラウザ回帰が成功。
6. main・既存商品・診断・SEO・ブランド・公開サイトはPRレビュー前に変更しない。

## 運用上の注意

- この変更が本番へ承認・公開された後の新しい測定データから品質評価を開始。公開前のデータを混ぜない。
- 運営者が `?test=1` を使わず操作した場合、通常利用と区別できない。QA開始時は必ず `?test=1`、終了時は `?test=0` を使う。
- GA4の受信抑止だけでは「すべてのイベントが実ユーザーによるもの」とは証明できない。ボット、データ欠測、同意・解析停止を考慮する。
- 未来の順序付きファネル・サービス別流入・楽天確定報酬は、データが十分蓄積した段階で別途検証する。
